# Running ColdDDI on a prepared dataset

`python scripts/run_benchmark.py` joins the existing LLM and diagnostic modules into one run. It does not change their scoring formulas. Run commands from the repository root.

## What the command runs

1. Check the dataset, splits, KG tables, and pair-level A/B annotations.
2. Resolve one model snapshot and record its file hashes.
3. Train a P4 LoRA adapter using Top-3 KG context.
4. Rescore the checkpoint candidates on each validation split and select a checkpoint separately for S0, S1, and S2.
5. Evaluate all three test splits. For S2, also score name masking, entity masking, and joint masking (R0–R3), including every directed swap anchor and target.
6. Write KPS/KSAI indicators, A–B gaps, coverage counts, predictions, and AUROC/average precision.

The scope is one model × P4 × one seed. The R0–R3 diagnostic recipe is defined for P4; this runner does not accept other prompt patterns. It does not reconstruct a dataset from raw XML, run the eight conventional baselines, or launch the complete paper experiment grid.

## Install and try it

Use a fresh Python environment. Install the PyTorch build for your CPU or CUDA setup, then:

```bash
python -m pip install -r requirements-benchmark.txt
python scripts/run_benchmark.py --data data/public/intermediate --ab-parquet annotations/ab_sample.parquet --model tiny-random-qwen --smoke --device cpu
```

The first run downloads the model from Hugging Face. `tiny-random-qwen` resolves to `yujiepan/qwen2.5-tiny-random`; its weights are random and its scores have no scientific meaning. `qwen-0.5b` resolves to `Qwen/Qwen2.5-0.5B`. To check a pretrained model on the same small sample, replace the model with `qwen-0.5b` and let the runner select CUDA when available.

Other model IDs or local model directories must be compatible with the existing Qwen/Llama/Gemma/Mistral prompt templates and LoRA target modules. The existing scorer requires `" Yes"` and `" No"` to each be a single tokenizer token; incompatible tokenizers fail rather than silently changing the scoring rule. A local directory's path must include its family name, because the existing prompt builder infers the family from that path. Model-supplied Python code is not enabled. The Qwen models above are the tested choices; naming a supported family alone does not establish model compatibility.

`--smoke` uses at most 16 training examples, 8 validation examples per split, and 16 test examples per split (half positive, half negative), one epoch, LoRA rank 4, and a 512-token context. The same training, selection, inference, and diagnostic code runs in both modes. Swap targets come from the full S1/S2 search pool, so the diagnostic prediction table is larger than the capped test set.

Without `--smoke`, no sample caps are applied. Defaults are four epochs, LoRA rank/alpha 16, learning rate `5e-4`, warmup ratio `0.05`, and a 1,250-token context, taken from the existing paper preset. Micro-batch size defaults to 1 with 16-step gradient accumulation to reduce memory use. `--batch-size` may be 1, 2, 4, 8, or 16; accumulation adjusts to keep an effective batch of 16. This is not a guarantee of bitwise equivalence to a different hardware or batching setup.

The runner uses the existing fixed epoch-0 training negative set throughout training. It does not cycle through cached negative sets. Checkpoints are saved/evaluated each epoch; selection uses the existing top-two-by-loss candidate rule followed by validation AUROC. All actual settings are recorded in `config.json`. These choices make a reproducible run configuration, not a claim that one command reproduces every number in the paper.

## Input layout

`--data` is the directory containing `filtered/` and `splits/`, not a CSV, XML, or pickle file. `--ab-parquet` is required explicitly; the runner never substitutes toy annotations for missing full-data annotations.

```text
intermediate/
├── filtered/
│   ├── drugs.csv
│   ├── ddi_edges.csv
│   ├── drug_enzymes.csv
│   ├── drug_targets.csv
│   ├── drug_transporters.csv
│   ├── drug_carriers.csv
│   └── drug_pathways.csv
└── splits/seed42/
    ├── manifest.json
    ├── train.parquet
    ├── val_s0.parquet
    ├── val_s1.parquet
    ├── val_s2.parquet
    ├── test_s0.parquet
    ├── test_s1.parquet
    ├── test_s2.parquet
    ├── negatives/
    │   └── {val,test}_{s0,s1,s2}.parquet
    └── train_negatives/           # optional; otherwise generated by existing sampler
        └── epoch_0.parquet
```

The KG tables can be Parquet instead of CSV; if both exist, Parquet takes precedence. The other two filtered tables must be CSV. Use consistent string drug IDs across all files; prefixing numeric IDs avoids CSV type-inference surprises.

| File | Required columns / contents |
|---|---|
| `drugs.csv` | `drugbank_id`, `name`, `smiles`; unique, nonempty IDs and names. Missing SMILES are permitted for P4. |
| `ddi_edges.csv` | `drug_a_id`, `drug_b_id`; the full known-positive edge table. |
| Each positive or negative split | `drug_a_id`, `drug_b_id`; no self-pairs or duplicate pairs, including reversed duplicates. Separate files determine labels; a `label` column is not used. |
| Enzyme / target / transporter / carrier KG tables | `drugbank_id`, `<type>_id`, `<type>_name`: e.g. `enzyme_id`, `enzyme_name` for enzymes and `target_id`, `target_name` for targets. Optional `organism`, `action`. |
| Pathway KG table | `drugbank_id`, `pathway_id`, `pathway_name`. |
| A/B Parquet | `drug_a_id`, `drug_b_id`, `pk_pd_label`, `has_key_entity`, `key_entity_name`, `key_entity_type`. |

The A/B file must cover exactly the positive pairs in `ddi_edges.csv`. `pk_pd_label` accepts `PK`, `PD`, `Mixed`, or `Unknown` (case-insensitive). `has_key_entity` must be a true boolean column, not strings such as `"False"`. Type-A rows need a nonempty entity name and type. Empty KG tables must still carry their column headers.

`manifest.json` follows the format written by the existing split builder:

```json
{
  "seed": 42,
  "g1_drugs": ["drug-1", "drug-2"],
  "g2_drugs": ["drug-3", "drug-4"]
}
```

This is only a schema illustration, not a runnable four-drug benchmark. The groups must be nonempty, disjoint, and together cover `drugs.csv`. If the manifest also contains `n_pairs`, its counts must match all seven positive split files. Training/S0 pairs contain only G1 drugs, S1 contains one G1 and one G2 drug, and S2 contains only G2 drugs. Positive folds must be disjoint; negatives must not be known positives. Every training/validation/test fold needs both classes. S2 must have eligible positive drug-swap candidates for L6.

The shipped negative sampler permits some training negatives to recur in S0 evaluation. The runner reports those overlaps in `input_report.json`; it does not silently change the sampling protocol. Input validation checks structure and consistency, not whether a new dataset's biological annotations are correct. Preparing those annotations remains the dataset author's responsibility.

## Full DrugBank or your own data

After the README's reconstruction command completes, run:

```bash
python scripts/run_benchmark.py --data data/private/intermediate --ab-parquet data/private/outputs_full/annotations/ab.parquet --model qwen-0.5b
```

For a different conforming dataset, change both paths. Nothing in the runner assumes 86, 800, or 1,900 drugs. A useful first check is:

```bash
python scripts/run_benchmark.py --data /path/to/intermediate --ab-parquet /path/to/ab.parquet --check-only
```

This validates the inputs without downloading weights, training, or writing output files. An arbitrary DDI table without the KG, split definitions, negatives, and A/B annotations is not sufficient. It must first be adapted to the format above. This command does not provide such an adapter or reproduce the original DrugBank benchmark from a different dataset.

## Outputs and resuming

By default, the output name contains the model, seed, dataset fingerprint, and smoke/full mode. Set `--output runs/my-run` to choose another directory. An existing nonempty directory is never overwritten unless the exact same run is continued with `--resume`.

| Output | Contents |
|---|---|
| `config.json`, `input_report.json` | Resolved settings, dependency versions, model/code/data hashes, validation counts and warnings. |
| `status.json` | Current stage, failure message if any, and hashes of completed artifacts. `complete` is written only after every stage succeeds. |
| `ckpts/`, `training_complete.json`, `manifest.json` | Training checkpoints and selected checkpoint / validation AUROC for each split. |
| `effective_counts.json`, `swap_candidates.parquet` | Actual sample counts and directed drug-swap triples. |
| `test_S0.csv`, `test_S1.csv`, `test_S2.csv`, `metrics.json` | Labeled test predictions, AUROC, and average precision. |
| `predictions_S0_R0.parquet`, `predictions_S1_R0.parquet`, `predictions_S2_R{0,1,2,3}.parquet` | Pair IDs, probabilities, and prompts. S2 includes the swap prediction set. |
| `indicators.csv`, `ab_gaps.json`, `coverage.json` | Diagnostic means, standard deviations, sample counts, A–B gaps and annotation coverage. |

Repeat your original command with `--resume` to continue. Finished stages are reused only after their artifact hashes are checked. Training resumes from its latest saved checkpoint; inference resumes from a partial prediction file. Work since the last saved checkpoint/batch may be repeated. Matching completed runs are verified and returned without training again.

Changed settings, data, code, model weights, or recorded dependency versions require a new `--output`. An output-directory lock prevents two processes from updating the same run. A failed run exits nonzero. Missing required prediction pairs, nonfinite probabilities, and failed checkpoint scoring are errors, not silently skipped rows.

Keep input files and local model files unchanged while a run is in progress. A shared drive needs working file locks. The runner records versions and fingerprints but does not promise identical floating-point results across different hardware.

Indicators are reported for populated buckets only. `ALL` uses positive anchors, following the existing implementation. If a dataset/sample has no usable pairs in one of PK-A, PK-B, PD-A, or PD-B, the A–B gap is `null` with an explanation, not zero. This is common for a small smoke sample.

Large runs require substantially more time, memory, disk, and GPU capacity. R0–R3 requires four S2 inference passes, and saved prompts can be large. Outputs may contain licensed data in prompts and pair IDs; keep them local unless you have permission to redistribute them.

## Tests

Offline input, cache, and diagnostic contract tests:

```bash
python -m pytest tests/test_benchmark_runner.py -q
```

Real CPU integration tests (downloads the tiny model on first use; runs both capped and uncapped toy data, independently recomputes every indicator cell, and checks resume behavior):

```bash
# Linux / macOS
COLDDDI_RUN_INTEGRATION=1 python -m pytest tests/test_benchmark_integration.py -q
```

```powershell
# PowerShell
$env:COLDDDI_RUN_INTEGRATION = "1"
python -m pytest tests/test_benchmark_integration.py -q
```

Once enabled, a model download or training failure fails the integration test; it is not treated as a passing or skipped run.

### Verification environment and limits

The new runner's 35 offline tests and 10 opt-in integration tests pass (45 total). This includes resumed partial inference, verification of completed runs, refusal to overwrite or reuse changed configurations/artifacts, and independent recomputation of the indicator table.

The new entry point has been exercised on Windows with Python 3.13.7, PyTorch 2.11.0+cu128, Transformers 4.57.1, PEFT 0.17.1, NumPy 2.1.2, pandas 3.0.2, and PyArrow 24.0.0. CPU checks use the tiny random Qwen model; a separate CUDA smoke run uses pretrained Qwen2.5-0.5B on an RTX 5090. Both produce all required R0–R3 predictions. The uncapped toy run uses all 874 training pairs and 198 / 1,152 / 356 S0 / S1 / S2 test pairs. These checks do not establish full-scale DrugBank performance or hardware requirements.

The existing diagnostic, split, and prompt/retrieval regression subset reports 438 passed and 18 skipped in this environment. A separate run of the existing L2/L3/L5 tests reports 26 passed, 3 skipped, and 6 failed: the older tiny-Llama fixture tokenizes `" Yes"` and `" No"` as two tokens, conflicting with the scorer contract. Those existing tests and the underlying training/scoring modules have not been modified. The new integration tests use the compatible tiny-Qwen fixture instead; the whole repository test suite is not claimed to be green.
